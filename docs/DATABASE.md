# DATABASE.md — Supabase + pgvector

Implementa o TCC §3.4. Todo acesso passa pelo back-end com a chave `service_role`; o app
Flutter **nunca** fala com o Supabase.

## 1. Extensões

```sql
create extension if not exists vector;
create extension if not exists pg_trgm;
```

Confirme a versão instalada no projeto:

```sql
select extversion from pg_extension where extname = 'vector';
```

## 2. Schema

```sql
create table documento (
  id            bigint generated by default as identity primary key,
  titulo        text not null,
  tipo_fonte    text not null check (tipo_fonte in ('livro','bula')),
  referencia    text not null,          -- "Spinosa et al. (2017)"
  indice_versao text not null,          -- data + hash do corpus
  criado_em     timestamptz not null default now()
);

create table chunk (
  id           bigint generated by default as identity primary key,
  chunk_id     text not null unique,    -- "spinosa-c22-p574-003"
  documento_id bigint not null references documento(id) on delete cascade,
  texto        text not null,
  texto_hash   text not null,           -- idempotência do ETL
  capitulo     text,                    -- só chunk de livro (tipo_fonte='livro')
  secao        text,                    -- só chunk de bula: "posologia", "interacoes"...
  origem       text,                    -- só chunk de bula: "humana" | "veterinaria"
  produto      text,                    -- só chunk de bula: nome comercial do ciclo/apresentação
  pagina       int,
  farmacos     text[] not null default '{}',
  especies     text[] not null default '{}',
  tokens       int not null,
  embedding    vector(1536) not null,   -- gemini-embedding-001, MRL 1536
  fts          tsvector generated always as (to_tsvector('portuguese', texto)) stored,
  criado_em    timestamptz not null default now()
);
```

`capitulo` e `secao` são mutuamente exclusivos por `tipo_fonte` — um chunk de livro
preenche `capitulo` e deixa `secao`/`origem`/`produto` nulos; um chunk de bula faz o
oposto. Nenhuma `check constraint` força isso (`etl/load.py` já garante pela origem dos
dados — manifesto de bula vs. mapa de capítulos do livro, nunca os dois no mesmo chunk).

### Por que 1536 e não 3072

`gemini-embedding-001` gera 3072 dimensões por padrão, mas o índice **HNSW do tipo
`vector` só suporta até 2000 dimensões**. Duas saídas válidas: (a) reduzir para 1536 via
Matryoshka, com normalização L2 manual — **é o que este projeto faz**; (b) manter 3072 e
indexar com cast para `halfvec`:

```sql
-- alternativa (b), caso se opte por 3072
create index on chunk using hnsw ((embedding::halfvec(3072)) halfvec_cosine_ops);
```

Ver `DIVERGENCIAS.md` §3. O TCC não trata desse limite; é uma restrição de
implementação, não uma mudança de desenho.

## 3. Índices

```sql
create index chunk_embedding_hnsw on chunk
  using hnsw (embedding vector_cosine_ops)
  with (m = 16, ef_construction = 64);

create index chunk_fts_gin      on chunk using gin (fts);
create index chunk_farmacos_gin on chunk using gin (farmacos);
create index chunk_especies_gin on chunk using gin (especies);
create index chunk_secao_idx    on chunk (secao);
create index chunk_origem_idx   on chunk (origem);
```

Nas sessões de consulta: `set local hnsw.ef_search = 100;` (default 40 — 100 favorece
recall, que é a métrica do Quadro 1).

## 4. Funções

```sql
create or replace function buscar_semantico(
  consulta_embedding vector(1536),
  filtro_especies    text[] default null,
  filtro_farmacos    text[] default null,
  qtd                int    default 30
)
returns table (chunk_id text, texto text, similaridade float, pagina int, capitulo text)
language sql stable
as $$
  select c.chunk_id,
         c.texto,
         1 - (c.embedding <=> consulta_embedding) as similaridade,
         c.pagina,
         c.capitulo
  from chunk c
  where (filtro_especies is null or c.especies && filtro_especies)
    and (filtro_farmacos is null or c.farmacos && filtro_farmacos)
  order by c.embedding <=> consulta_embedding
  limit qtd;
$$;
```

O operador `<=>` é distância de cosseno; a similaridade é `1 - distância`.

A função lexical abaixo existe como **sinal auxiliar e fallback**. O BM25 canônico do
pipeline roda em `bm25s` no back-end (`RAG_SPEC.md` §3.2), porque `ts_rank_cd` não
computa IDF verdadeiro:

```sql
create or replace function buscar_lexical(
  termos text,
  qtd    int default 30
)
returns table (chunk_id text, texto text, escore float)
language sql stable
as $$
  select c.chunk_id, c.texto,
         ts_rank_cd(c.fts, plainto_tsquery('portuguese', termos)) as escore
  from chunk c
  where c.fts @@ plainto_tsquery('portuguese', termos)
  order by escore desc
  limit qtd;
$$;
```

## 5. Segurança

```sql
alter table documento enable row level security;
alter table chunk     enable row level security;
-- Sem políticas para anon/authenticated: acesso só via service_role no back-end.
```

Nenhuma tabela guarda dado de paciente, tutor ou consulta clínica. O histórico de
consultas vive apenas no `hive_ce` do aparelho. Essa separação é o que sustenta a
afirmação de privacidade do TCC §4.6.

## 6. Free Tier — cuidados operacionais

- Limite de 500 MB. O corpus indexado (livro + bulas, ~1536 dims) cabe com folga;
  monitore com `select pg_size_pretty(pg_total_relation_size('chunk'));`.
- **Projetos são pausados após 7 dias sem atividade de banco**, e a retomada leva
  ~30 s. Durante a janela de coleta de telemetria (TCC §5, blocos de julho a outubro),
  mantenha um *ping* agendado — um projeto pausado no meio da coleta contamina as
  medições de latência.
- Egress de 5 GB/mês: suficiente para o volume previsto de ~500 consultas.

## 7. Migrações

Arquivos versionados em `backend/migrations/NNN_descricao.sql`, aplicados via Supabase
CLI. Nunca edite o schema pelo painel web sem gerar a migração correspondente — o
`indice_versao` precisa ser reproduzível para a rastreabilidade científica exigida em
TCC §4.7.
